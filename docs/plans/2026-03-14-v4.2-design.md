# A11y Crawler v4.2 — Non-text Contrast (WCAG 1.4.11)

> Builds on v4.1 pipeline. Scope: single new WCAG test + frontend verification.
> Approved design — Approach B (evaluate extracts colors, contrast math in Node).

## Scope

### What We're Detecting

WCAG 1.4.11 requires that visual indicators of UI components have at least 3:1 contrast ratio against adjacent colors. The most common real-world failure: form inputs with light gray borders on white backgrounds — users with low vision can't tell where the field starts and ends.

This is a **full gap in open-source axe-core** (only available in axe DevTools Pro). Implementing it gives the crawler a capability that most free accessibility tools lack.

### Scope Boundaries

**In scope (a)**:
- Borders of interactive elements (`button`, `input`, `select`, `textarea`, `[role="button"]`, `[role="checkbox"]`, `[role="radio"]`, `[role="switch"]`, `[role="slider"]`, `[role="tab"]`)
- Contrast of border color against both adjacent colors (element background + parent background)
- Alpha-blending for semi-transparent borders
- Template amplification (structural issue — same CSS applies to all template pages)

**Out of scope**:
- Elements without visible borders (scope (a) — skip, no false positive risk)
- Links (`<a>`) — covered by axe-core `color-contrast` rule (WCAG 1.4.3)
- SVG icons (fill/stroke vs background)
- Gradients (would need pixel sampling)
- Outline properties (keep scope tight for v4.2)
- Focus indicator contrast (`:focus` state — separate concern)

## Architecture: Approach B — Hybrid Evaluate + Node Math

### Why Not All-in-Evaluate (Approach A)

The WCAG contrast formula (sRGB → linearRGB → relative luminance → ratio) is ~15 lines of math, but getting it wrong produces silently incorrect results. Approach B puts the math in a separate module that can be unit-tested with known W3C reference values. The overhead of serializing ~20-50 color pairs is negligible.

### Component 1: `src/analyzer/contrast.ts` — Pure Math

```typescript
/**
 * Parse CSS color string to [R, G, B, A] (0-255 for RGB, 0-1 for A).
 * Handles rgb(), rgba(). getComputedStyle() always resolves to these formats.
 */
export function parseRgba(css: string): [number, number, number, number] | null

/**
 * Alpha-blend foreground (with alpha) over opaque background.
 * result_channel = fg * alpha + bg * (1 - alpha)
 */
export function alphaBlend(
  fg: [number, number, number, number],
  bg: [number, number, number],
): [number, number, number]

/**
 * sRGB channel (0-255) → linear RGB (0-1).
 * Threshold at 0.04045 per IEC 61966-2-1 / WCAG 2.2 spec.
 * Below: C / 12.92. Above: ((C + 0.055) / 1.055) ^ 2.4
 */
export function srgbToLinear(channel: number): number

/**
 * WCAG 2.x relative luminance from [R, G, B] (0-255).
 * L = 0.2126 * R_lin + 0.7152 * G_lin + 0.0722 * B_lin
 */
export function relativeLuminance(rgb: [number, number, number]): number

/**
 * WCAG contrast ratio between two luminance values.
 * Returns value >= 1.0 (order-independent).
 * Formula: (lighter + 0.05) / (darker + 0.05)
 */
export function contrastRatio(l1: number, l2: number): number
```

**Unit tests** with W3C reference values:
- White (255,255,255) vs Black (0,0,0) = 21:1
- Known color pairs from the WCAG spec
- Alpha-blending: rgba(200,200,200,0.5) on white = rgb(228,228,228)
- Edge cases: fully transparent (alpha=0) → ratio = 1:1

### Component 2: `testNonTextContrast()` in `src/analyzer/wcag-tests.ts`

**Elements inspected**: `button`, `input`, `select`, `textarea`, `[role="button"]`, `[role="checkbox"]`, `[role="radio"]`, `[role="switch"]`, `[role="slider"]`, `[role="tab"]`.

> Not `<a>` — links are textual content covered by axe-core's `color-contrast` (WCAG 1.4.3).

**The `page.evaluate()` extracts per element**:

```typescript
interface ElementColorData {
  selector: string;
  html: string;                        // outerHTML truncated to 200 chars
  sides: Array<{
    side: "top" | "right" | "bottom" | "left";
    borderColor: string;               // e.g. "rgba(200, 200, 200, 0.5)"
    borderWidth: number;               // px
  }>;
  elementBg: string;                   // background of the element itself (inner adjacent)
  parentBg: string;                    // first ancestor with non-transparent bg (outer adjacent)
}
```

**Evaluate logic**:
1. Iterate interactive elements with `rect.width > 0 && rect.height > 0` (visible only)
2. `getComputedStyle()` → extract individual sides: `borderTopColor`/`borderTopWidth`, `borderRightColor`/`borderRightWidth`, etc.
3. Filter sides where `parseFloat(borderWidth) > 0` — if none have border, skip element
4. Extract `backgroundColor` of the element itself
5. DOM walk up `parentElement` chain for `parentBg`: first ancestor with `backgroundColor` that is NOT `transparent` / `rgba(0, 0, 0, 0)`. Fallback: `rgb(255, 255, 255)` (white)
6. Return data

**Node-side processing**:
1. For each side with border:
   - `parseRgba()` the borderColor
   - `alphaBlend()` against `elementBg` → `contrastRatio()` — is it < 3.0?
   - `alphaBlend()` against `parentBg` → `contrastRatio()` — is it < 3.0?
2. If border fails against **either** adjacent color → create issue
3. Report the worst ratio found in the description

**Error handling**: Wrap evaluate in try/catch so a failure doesn't kill other tests running in `Promise.all`.

**Performance**: ~50-100ms in evaluate (getComputedStyle + DOM walk per element) + ~5ms Node math. Heavier than other Tier A tests but still evaluate-only (no DOM mutation, no viewport change).

## Backlog (v4.3+)

- **Color contrast swatch UI**: Visual badge in issue cards showing the two colors and ratio (`██ #e0e0e0 vs ██ #ffffff → 1.3:1 ❌`). Requires passing RGB values as issue metadata and a new `ColorContrastBadge` frontend component. Strong SaaS differentiator.
- **Outline contrast**: Check `outlineColor`/`outlineWidth` for elements that use outlines instead of borders (Material UI pattern).
- **Focus indicator contrast**: Check `:focus` state contrast — requires evaluating elements in focused state.
- **SVG icon contrast**: `fill`/`stroke` vs background for inline SVGs used as interactive indicators.
- **Gradient handling**: Use average color or pixel sampling for gradient backgrounds/borders.
